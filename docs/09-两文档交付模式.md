# 两文档交付模式（默认模式）

> 用户要的不是流程，是两份能直接复制粘贴的文档：
> 1. **《资产提示词》**：人物、场景、道具——每张图标明推荐出图模型（`docs/10`），复制到对应模型出图，或接上 API 用 `tools/image_gen.py` 批量出；
> 2. **《Seedance 提示词》**：按剧情逐条、带时间戳，每条有 A 预演版 / B 无预演版两套——上传资产后复制到 Seedance 2.5 全能参考出片，拼起来就是整部片。
>
> 前面所有岗位的价值，必须体现在这两份文档的每一句里，而不是体现在内部审核记录里。
> 本模式是工厂的**默认模式**。完整模式（`docs/01`）和精简模式（`docs/08`）只在用户明确要求时使用。

---

## 一、只有两个用户确认点

```
① 故事确认 ──→ ② 剧本确认 ──→ 后台一次合成 ──→ 交付两份文档（+ 可选白模预演视频）
```

- **① 故事确认**：一句话故事 + 分条大纲 + 立项默认设定（风格、画幅、入口），一条消息给用户。
- **② 剧本确认**：剧本 + 分条表（每条时长、结构、台词），一条消息给用户。
- 剧本确认之后**不再停下来问用户**，直到两份文档交付。用户确认后不追加 AI 复核。

## 二、后台怎么合成（一次通过，不来回）

剧本确认后，由**一个执笔者**（Seedance 编译师牵头）一次写完两份文档。其他岗位不再作为"轮流交稿、轮流审核"的环节，而是作为**执笔时必须逐项过一遍的视角清单**，体现在文档里：

| 视角（原岗位） | 必须落进文档的东西 |
|---|---|
| 总导演 / 文戏导演 | 每条的视觉论点、时间结构、调度与镜头覆盖、特写给谁、轴线 |
| 摄影指导（兼灯光） | 每镜视场角、机位、主运镜起止、光源方向色温、色彩、质感后缀 |
| 美术指导（兼道具） | 场景描述锁、空间地图、道具计数归属与操作机制 |
| 角色造型师 | 角色描述锁（逐字复用）、三视图单图标准、状态变体 |
| 表演指导 | 目标/隐藏/眼神任务/手上的事、情绪累积时机 |
| 台词对白导演 | 每句台词第几秒、谁说、语气、停顿、口型约束 |
| 声音导演 | 音色锁、现场声清单、逐镜声音、静默、跨条声音桥 |
| 武戏 / VFX 导演 | 受力因果、损坏继承、特效七要素与尺度锁（有此类场次时） |
| 风格参考总监 | 参考片拆出的介质、光色、节奏参数（有参考时） |
| Image 2.5 资产提示词大师 | 资产文档的每张图提示词与 Seedance 引用语 |
| 合规官 | 无年龄词、无文字车标、真人与版权、尺度——直接写进提示词，不另出报告 |
| 场记 | 条与条之间的入口/出口状态、道具与伤湿的继承 |

**唯一的内部检查**：写完后执笔者自己跑一遍
1. `python3 tools/prompt_lint.py`（每条 Seedance 提示词）；
2. 《圣经》第十节"提交前十六问"；
3. 复杂度预算（`docs/06` 杠杆 4）。

发现问题**就地改掉**，不退回、不开会、不出审核报告。复杂度红色的条目直接拆条再写。

## 三、交付物格式

### 3.1 《资产提示词》`交付/01-资产提示词.md`
模板：`templates/交付-资产提示词模板.md`
- 开头一张出图清单：序号、标签、类型、文件名、依赖哪张图、用于哪几条视频。
- 按出图顺序排列：人物三视图 → 状态变体 → 道具 → 场景主图 → 场景宫格 → （多人戏）站位示意图 → （需要时）首帧图。
- 每张图：一行用途 + 一个可直接复制的提示词代码块 + 三到五条"出图后一眼检查"。
- 不放审核表、修订记录、内部讨论。

### 3.2 《Seedance 提示词》`交付/02-Seedance提示词.md`
模板：`templates/交付-Seedance提示词模板.md`
- 开头一张总表：条号、时长、画幅、上传哪些资产（按上传顺序）、这条讲什么。
- 每条一节：
  1. **上传清单**（按顺序：@图片1 = 哪个文件 …；有白模预演时 @视频1 = 哪段预演）；
  2. **界面参数**（模式、时长、画幅、分辨率、音频开）；
  3. **一个可直接复制的完整提示词代码块**——包含素材职责、人数锁、空间、首帧、角色锚点、摄影规格、带时间戳的剧情与表演、台词、音效、VFX（有则写）、光与质感后缀、肯定约束与失败判据；
  4. **拼接说明**一行：这条的出口状态接下一条哪里、声音桥。
- 文末一行：剪辑顺序与总时长。

### 3.3 每条两个版本：A 预演版 / B 无预演版

每条都交两个可直接复制的提示词，用户按手头条件选一个上传：

| | **A 预演版** | **B 无预演版** |
|---|---|---|
| 上传 | 资产图 + `@视频1 = previs_<条号>.mp4`（白模预演，只给结构） | 只有资产图；需要时加一张**首帧图**（`@图片N`，由出图模型按首帧提示词出） |
| 结构从哪来 | 预演视频：切点、机位、焦段、运镜、人物路线、事件先后 | 文字：每镜的机位高度、距离、焦段、起止构图、人物位置全部写成数字（《圣经》第 21–23 条），切点清单（第 28 条） |
| 时间轴写法 | 每行写"（同预演 X–Y 秒）"（第 25 条） | 不出现"预演""@视频"字样 |
| 适合 | 调度复杂、有高度差、长镜头里距离变化大、巨物尺度、多人走位（第 24 条触发项） | 调度简单、单人或双人固定站位、文戏、用户不装 Blender |
| 代价 | 多一步 Blender（`tools/previs/`，按镜头规格 JSON 自动渲染） | 抽卡风险更高；第 24 条触发的条要在"最可能翻车"里写明 |

规则：
1. **两个版本讲同一场戏**：镜头数、切点、景别、台词、声音、角色锁、空间地图逐字一致。区别只在素材职责第一行（A 有 @视频1 职责句）、时间轴的"同预演"标注，以及 B 版把预演承担的结构改写成数字。
2. **每条写一行推荐**：`**推荐**：A 版（理由：第 24 条——有约 3 米高差的爬升）` 或 `**推荐**：B 版（理由：双人固定站位，文字足够）`。
3. **B 版的首帧图**：第 24 条触发、但用户选 B 版时，资产文档里给这条加一张首帧图，B 版素材职责写"@图片N 是本条首帧：只取第一帧的构图、人物位置与朝向"。
4. 交付文档格式：每条一节，节内依次是 `### A 预演版`（上传清单、界面参数、画外禁名、长镜头理由（有则写）、预演对照表、提示词代码块）和 `### B 无预演版`（上传清单、界面参数、提示词代码块）；推荐、最可能翻车、拼接写在两个版本之后。
5. `tools/prompt_lint.py --all` 分别检查两个版本：A 版每行要对应预演段，B 版不得出现"预演"和"@视频"。

## 四、白模预演（`crew/25-previs-director`，A 版的结构来源）

每条都出预演（A 版要用）；以下情况在推荐行里推荐 A 版：
- 复杂调度（3 人以上同场走位、追逐、打斗）；
- 一镜到底里的复杂运镜路径；
- 用户想先看节奏和机位再出片。

做法：写一份镜头规格 JSON（`tools/previs/README.md`），用 `tools/previs/render_previs.py` 无界面调用 Blender 渲染；或用 Blender MCP 手工搭。以圆柱 + 球头的代理人物、简化场景和圆滑运镜，按分条表做出每条的结构预演视频，作为 `@视频1` 只提供**镜头路线、构图、空间、人物整体路线与事件先后**；脸、服装、表演、质感全部由资产图和提示词决定。预演视频与两份文档一起交付；用户看过预演认可后直接用，不再追加复核。

## 五、给用户的消息最少化

- 后台合成期间不推送中间稿、不逐个汇报岗位进度。
- 交付时一条消息：两份文档的链接、出图总张数、视频总条数与总时长、每条最可能翻车的一个点和对应的一行改法。
